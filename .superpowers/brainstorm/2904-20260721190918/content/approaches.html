三個問題的解決方案比較

針對 OCR 數量混淆、新增倉庫存量欄位、漏品項三個問題，提出兩種方案路徑

方案 A：最小改動 — 純 Prompt 修正 (Recommended)

只改 Gemini prompt + 新增一個欄位，不改資料庫結構

變更範圍
檔案 改動 風險
ocr.ts（兩處 prompt） 修正 prompt 區分「補貨量」vs「總倉庫存量」、新增 warehouse_quantity 提取要求、強調「不要漏任何品項」 低
types.ts (PageItem, ImportDrugItem) 新增 warehouse_quantity 欄位 低
DrugCard.tsx 卡片顯示倉庫存量（與數量並排） 低
PreviewPanel.tsx 預覽表格新增倉庫存量欄 低
pdfParser.ts (ParsedItem, ParsedPdf) 型態新增 warehouse_quantity 低

優點

  • 改動最小，不牽動資料庫 migration
  • 不影響現有掃描/清點流程
  • 實施快速（1-2 小時）

缺點

  • 倉庫存量不會持久化到 DB（僅匯入時顯示）
  • 漏品項只能靠 prompt 約束，無自動偵測/補救

方案 B：完整方案 — Prompt + 輕量驗證層

方案 A 的改動 + 新增頁面項目數驗證 + 倉庫存量可選持久化

額外變更（在方案 A 基礎上）
檔案 改動 風險
ocr.ts 每批 OCR 後驗證該頁項目數 ≈ 44（±2 容忍），不足時自動重試或標記警告 中
ocr.ts 新增頁碼連續性檢查（1→2→3...），跳頁時警告 中
ImportOverlay.tsx 匯入前顯示總項數確認摘要（e.g. "辨識 262/264 項，2項可能有漏"） 低

優點

  • 漏品項有主動偵測與使用者提示
  • 頁碼連續性驗證增加資料可靠性
  • 使用者可在匯入前看到異常警告

缺點

  • 需要更多實作時間（3-4 小時）
  • 頁碼偵測依賴 OCR 準確度（OCR 本身可能錯頁碼）
  • 驗證邏輯可能誤報（如末頁不足 44 項是正常的）
A

方案 A — 最小改動

純 prompt 修正 + 新增 warehouse_quantity 欄位 + UI 顯示。快速、低風險。

B

方案 B — 完整方案

方案 A + 頁面驗證 + 漏品項警告提示。更可靠但實作時間較長。
